# Module contracts

Website lead integration: Bearer-only POST `/integrations/website/leads` accepts strict bounded inquiry fields and a stable `form-submissions:<id>` or `appointments:<id>` event ID. `WEBSITE_LEADS_SECRET` is independent from scheduler/login secrets and must match the website's server-only `CRM_LEADS_SECRET`. No dashboard session/CSRF exemption is added to `/api`. The fixed receiver creates or matches a normalized-email Prospect, adds one immutable inquiry note per event, fills only blank profile fields, preserves existing stage/owner/consent/suppression, and never enrolls or sends email. New prospects receive unknown consent, the first open stage and an active owner. Additive `003_website_leads` provisions receipt hashes and recovery cursors on first use.

With `WEBSITE_LEADS_URL=https://sandiegowebsiteexperts.com/api/crm/leads`, authenticated scheduler run ticks recover stored website inquiries and appointments in bounded ascending-ID batches. The website feed requires the same private Bearer key and exports inquiry fields only. Immediate delivery and recovery share transactional event receipts. Persisted recovery starts five minutes before first activation; it does not bulk-import older leads. Network failure retains the cursor for retry and does not block mail processing; the mail worker receives a 12-second budget after the bounded recovery attempt. All public form validation/spam controls and existing notification email behavior remain on the website.

API base `/api`. JSON success is the value itself (collections normally `{items,total,page,pageSize}`). Error `{error:string, details?:unknown}`. Cookie session; `GET /api/auth/session` returns `{user:{id,name,email,role,permissions}|null, csrfToken:string}`. POST login `{email,password}` returns same authenticated shape. POST logout. Fetch credentials same-origin; send `x-csrf-token` on all non-GET dashboard calls. Public tracking/unsubscribe and Bearer scheduler routes exempt from CSRF.

`APP_URL` remains the actual dashboard and generated-link URL. `ALLOWED_ORIGINS` configures API-only CORS: blank permits the `APP_URL` origin; comma-separated exact canonical HTTP(S) origins add trusted origins; `*` permits any valid HTTP(S) API origin. Responses omit `Access-Control-Allow-Credentials`. Cookie sessions remain same-origin, with CSRF and server permissions enforced; wildcard CORS does not enable a separately hosted authenticated frontend. Environment changes require an application restart.

## Implemented refinements

- Database compatibility targets MySQL 8+ or MariaDB 10.11+ using the same Knex/mysql2 layer. All business tables explicitly use InnoDB. Local execution was verified on MariaDB 11.4.8; the actual Hostinger engine remains a verification gate.
- Mailbox password write fields are `smtp_password` and `imap_password`; responses expose only presence flags. A connection edit invalidates prior validation, and concurrent validation cannot approve a stale configuration.
- `send_attempts` keeps the stable logical message/attempt and a monotonic `submission_count`. `send_attempt_events` stores immutable per-submission outcomes, so a temporary rejection remains reportable after a later accepted retry.
- `messages` records per-message `open_tracking`/`click_tracking`, plus `reviewed_at`/`review_action`. `POST /api/inbox/:id/review` accepts `{action:'resume'|'stop'}`. Individual review decisions persist while another hold remains; human stops and suppression cannot be cleared through review.
- New manually written compose/reply jobs use `is_manual:true` and immutable normalized `manual_recipient`. Optional `contact_id` is logging metadata and never decides the SMTP recipient. `manualRecipientEligibility` checks that exact address for suppression and revoked consent at enqueue, reservation, and pre-submission; manual mail does not require campaign opt-in, create contacts, or upgrade consent. It retains live-send/global pause, active validated mailbox, fresh sync, rolling capacity, and unknown-outcome gates. Individually written manual mail skips campaign business-hour windows and campaign spacing. Campaign/test timing is unchanged. Manual messages require no business address and add no marketing footer. Signature and open tracking are explicit per-message options; omitted options preserve the original plain-mail behavior. Campaign/test consent and marketing rules are unchanged.
- Replies additionally include `reply_source_id` (original database message ID), normalized `reply_recipient` (`from_email` for inbound, `to_email` for outbound), and original threading headers. Reservation and pre-submission verify those anchors and any existing attempt/message recipient. New manual replies ignore legacy contact matches; older non-manual queued replies retain strict contact/source checks. Unanchored or drifting legacy replies are canceled for review, never silently retargeted. The legacy inbound matching API still rejects a contact whose email differs from the sender. Incoming reference matching accepts contactless messages only when references identify one external recipient in the same mailbox, and verifies the incoming sender before classifying a human reply.
- `email_accounts.last_sync_at` is the freshness gate and is invalidated during scanning/failure. `last_successful_sync_at` preserves the last complete catch-up time for health displays. UID SEARCH bounds actual messages rather than sparse numeric UID spans.
- Analytics denominators are `smtp_accepted_messages`, `open_tracking_messages`, `click_tracking_messages`, and `unique_recipients`; raw events and filtered unique counts remain separate. Qualified/won values are explicitly current agency stage snapshots.
- Reconciliation accepts optional `accepted_at` as an offset ISO timestamp supported by provider evidence. It must fall between reservation and now. Without an exact verified timestamp, confirmation time is the conservative follow-up baseline. A confirmed `not_sent` resolution explicitly queues a retry through all sending safeguards.
- Contact-list rows include real deal value/currency/outcome, next task, and latest note for the pipeline. Stage changes keep deal outcomes aligned. Sender replacement never changes existing enrollment/account associations.

## Live Inbox execution

Inbox list, outbox and selected thread refresh quietly every 10 seconds while visible; mailbox health refreshes every 30 seconds. Focus/online resumes refresh. Requests do not overlap, stale responses are discarded, and background failures preserve displayed mail and drafts. UI acceptance means SMTP accepted, never confirmed delivery. GET `/api/inbox/outbox?account_id=` returns up to 50 pending/held/failed manual jobs with id, account_id, recipient, subject, status, last_error and timestamps, without content/payload. Outbound messages expose send_status and accepted_at from their actual attempt/job.

POST `/api/inbox/process` accepts strict `{mode?:"inbox"|"sync"}` with session, CSRF and inbox:write; rate limit 20/min/user. It runs bounded work after a user queues compose/reply or requests sync. It never claims campaigns. Durable minute cron remains the browser-independent fallback. `inboxOnly` claims sync and strictly boolean is_manual send jobs; syncOnly takes precedence. Automatic receiving uses a minimum/default 60-second cadence using UTC polling buckets based on scan creation, with pending/leased sync deduplication.

Bearer-only POST `/internal/tick` accepts strict `{action?:"run"|"status"|"install"|"activate-inbox",mode?:"all"|"sync"|"inbox"}`. Existing empty-body callers retain all-job mode. Status returns aggregate job counts, mailbox IDs/state/timestamps and no message data or credentials. Install provisions only the fixed HOSTINGER_ACCOUNT/APP_URL-derived private scheduler directory; requests cannot choose paths or commands. Activation requires the live environment gate, locks settings, refuses leased sends, holds all preexisting queued sends, sets poll interval60/unpauses, audits, and records an idempotency marker. Repeating activation cannot release or hold newer work. It does not process mail. The configured cron uses inbox mode, so campaign work needs its own deliberately enabled scheduler.

## Mail composer, profiles, attachments and drafts

Compose and reply additionally accept `body_html?` (sanitized, 200000 characters), `include_signature?`, `signature?` (plain text, 10000 characters), `open_tracking?` and `attachments?` (`{filename,content_type,content_base64}[]`). At most 10 files and 5 MiB decoded total are accepted; file/URL/path/raw source options are rejected. Signature text is snapshotted at enqueue. Open tracking defaults off in the API; the new composer offers an enabled checkbox. A tracked manual message gets one stable opaque pixel token without campaign footer or unsubscribe additions. Retries reuse the stored content/token and attachments. Sender names come from contacts, connected mailbox names or MIME display names; avatars use initials and never fetch third-party profile images.

`message_details` stores names, a lightweight attachment manifest and encrypted attachment content. Message/list responses include `from_name`, `to_name`, safe `attachments`, `open_count`, `first_opened_at`, and `last_opened_at`; stored ciphertext and binary content are omitted. GET `/api/inbox/:id/attachments/:fileId` requires a session and returns an attachment download as application/octet-stream with nosniff/no-store/sandbox headers. Incoming MIME messages up to 8 MiB are parsed; up to 5 MiB of attachments are retained. Larger messages point the operator to webmail. Existing messages that were ingested before attachment storage keep their previous content.

GET/POST `/api/inbox/drafts`, GET/PATCH `/api/inbox/drafts/:id` operate on the current user only. POST creates, PATCH replaces, PATCH `{discard:true}` deletes. Draft writes require Inbox permission, session and CSRF; drafts and their summaries are encrypted with the existing encryption key. Draft bodies may be incomplete; a maximum of 50 drafts per user is enforced. A successful compose/reply with `draft_id` atomically removes that user-owned draft while queueing. Explicit Save draft & close persists the current editor, signature and files; Cancel closes without saving. Forward is a new compose with a forwarded text block and copied available attachments, with no reply headers.

The additive/idempotent migration `002_mail_features` provisions message_details and mail_drafts with parent-key charset/collation compatibility. The application provisions these exact tables before Inbox use or worker execution, so an existing hosted deployment can upgrade without running destructive SQL. The same migration is available to db:migrate. Scheduler status includes `mail_storage_ready`. The full regression suite uses isolated databases and fake SMTP only.

Open status means a tracking-image load was observed, never confirmed reading or delivery. No recorded open is inconclusive; image blocking, proxy caches, privacy protection and bots affect results. Bot filtering and the configured event retention apply. Dashboard HTML previews strip tracking pixels and remote images so reading your own sent email cannot record an open.

## Mailbox removal

DELETE `/api/accounts/:id` requires a session, CSRF and settings:write. It disconnects the account using an additive `deleted_at` tombstone, clears encrypted credentials/validation/default, cancels pending safe jobs, stops enrollments and pauses active campaigns. Historical messages, attachments, attempts and account identity are retained. Unknown SMTP attempts and held jobs remain for manual reconciliation. Leased work or submitting attempts return 409: retry after processing or lease recovery. No provider mailbox is deleted. Removed accounts are omitted from GET accounts and cannot be edited, validated, selected as default or synced. Reconnecting the same email through POST requires both passwords and reuses the historical identity with fresh validation; cancelled jobs and stopped enrollments never automatically resume. No replacement default is chosen automatically. Migration 004 is additive/idempotent and provisioned before account API use.
